# IDEAS.md

## TalkTune → Pocket Talk (MVP 피벗)

### Why

- 원래 TalkTune 컨셉(비주얼 아바타 + Pocket Talk + 습관 트래킹 + 오프라인 온디바이스)은 스코프가 넓고, 핵심 가정이 검증되지 않은 채 여러 기능이 얹혀 있었음.
- 경쟁 환경 재검토 결과:
  - **Speak**: 10억 달러 밸류에이션, 한국 영어 학습자 타겟 선점. 다만 구조화된 커리큘럼 + 즉각 교정 중심이라 "각잡고 공부하는" 경험에 가깝고, 가볍게 매일 대화하는 습관용으로는 결이 다름.
  - **Duolingo Max**: Video Call(Lily) + Roleplay를 이미 제공 중이고 2026년 7월 업데이트로 세션 길이도 늘림. "게임처럼 매일 조금씩" 컨셉은 이미 선점당한 상태 — 950M 다운로드, MAU 1.3억 규모의 배급력.
  - **범용 AI(ChatGPT 등)**: 무료 음성모드는 하루 15분 제한, 유료도 완전 무제한은 아님. 매일 대화 습관을 만들기엔 세션이 끊기는 경험이 이탈 요인.
- 위 세 경쟁자 모두 **화면 기반 UI**로 리텐션을 설계함 (피드백 카드, 시나리오 스크립트, 스트릭 애니메이션). "화면 없이 걸으면서 편하게 떠드는" 자리는 비어 있음.
- 온디바이스 추론은 클라우드 API 비용이 없기 때문에, 세션 길이를 인위적으로 제한할 유인이 없음 — 이게 "무제한으로 편하게 대화 가능"이라는 구조적 차별화로 이어질 수 있음.
- 그러나 이 모든 차별화 가설의 전제는 검증되지 않음: **"화면도 없고 게임화도 없이, 순수 음성 대화만으로 사람이 매일 돌아오는가"**는 아무도 증명한 적 없는 질문. 비주얼/게이미피케이션을 먼저 만들면 나중에 실패 원인(대화 자체 vs UI 요소)을 구분할 수 없음.

### What

기존 TalkTune 스코프를 극단적으로 걷어낸 MVP:

- **포함**
  - 순수 음성 대화 (화면: 시작/종료 버튼 + 세션 종료 후 한 줄 요약만)
  - 목소리 페르소나 1개 (톤 설계는 하되 애니메이션/아바타 없음)
  - 스트릭 숫자 표시만 (배지·레벨 등 게이미피케이션 없음)
  - 걷기 중 핸즈프리 사용을 염두에 둔 세션 흐름 (AI가 먼저 화제를 던지고, 침묵 감지 시 자연스럽게 전환)
- **제외 (검증 전까지)**
  - 비주얼 아바타 / 감정 애니메이션 (Rive 등)
  - 습관 트래킹 대시보드, 배지/레벨 시스템
  - 온디바이스 추론 — 이 단계에서 검증할 것은 "대화가 재밌는가"이지 "오프라인이 되는가"가 아니므로, 클라우드 API로 빠르게 프로토타입
  - 시나리오 라이브러리, 문법 교정 기능

### How

- **단일 검증 지표**: 첫 세션 이후 Day 3 / Day 7 재방문율.
  - 화면 보상도, 게이미피케이션도 없는 상태에서 "그냥 다시 얘기하고 싶어서" 돌아오는지가 이 아이디어 전체의 생사 판단 기준.
- **판단 기준**
  - 리텐션이 나오면 → 핵심 가정이 맞는 것. 이후 비주얼/게이미피케이션/온디바이스는 성장 레버로 순차 추가.
  - 안 나오면 → 비주얼이나 스트릭을 아무리 잘 만들어도 근본 가정이 틀린 것이므로, 방향 자체를 재검토.
- **진입/종료 UX 관련 기술 메모**
  - iOS에서 Siri App Intent로 잠금 화면 상태에서 앱을 포그라운드로 여는 것은 기본적으로 언락을 요구함 (`openAppWhenRun`). 완전 화면-프리 진입은 제약이 있으므로, 초기 진입(화면 켜짐 상태 3초)은 허용하고 이후 세션은 화면 off로 진행하는 절충안으로 설계.

## 이전 시도(Codex) 실패 원인 메모

당시엔 REPLWorks 방식을 몰라서 프로젝트 docs 폴더에 문서들(ARCHITECTURE.md, IDEAS.md 등)을 넣고 Codex한테 스텝바이스텝으로 개발을 맡겼음. 코딩은 진행됐는데 "테스트 어떻게 해?"라고 물으면 대답은 하는데 따라할 수 없고 환각이 생김.

원인으로 짚이는 것들:

1. **문서 구조 문제**: IDEAS.md 안에 비전/포지셔닝/리텐션 전략/비즈니스 모델/GTM/Exit까지 다 들어있고, 그 안에 기술 스택 표까지 끼어있었음. "왜 만드는가"와 "지금 뭘 만들어야 하는가"가 분리가 안 됨. iOS+Android 스택도 둘 다 완전한 형태로 명시돼 있어서 에이전트가 스코프를 못 좁힘.

2. **테스트 불가능한 기능을 에이전트에게 맡김 (진짜 원인일 가능성 높음)**:
   - `SFSpeechRecognizer`는 시뮬레이터에서 인식 자체가 불안정하다고 Apple 개발자 포럼에도 다수 보고돼 있음 — 실기기 테스트 필수.
   - `FoundationModels`(온디바이스 LLM)는 Apple Intelligence 활성화된 A17 Pro 이상 기기, 그리고 Mac 자체도 Apple Intelligence 지원해야 시뮬레이터에서도 동작. 일반 CI/터미널 기반 코딩 에이전트 환경에서는 이 조건을 만족 못 시킴.
   - 블루투스 핸즈프리 + 백그라운드 오디오 흐름은 사람이 직접 걸으면서 들어봐야 검증되는 종류라 애초에 "코드로 실행해서 확인" 자체가 불가능.
   - → 에이전트가 자기가 짠 코드를 스스로 실행/검증하는 피드백 루프가 없는 상태로 계속 코드만 생성. "테스트 어떻게 해?"라고 물으면 실제로 돌려본 적이 없으니 그럴듯한 절차를 지어낼 수밖에 없었던 것으로 보임.
   - "가장 중요한 목표는 삭제되지 않는 것" 같은 철학적 문장도 에이전트에겐 구현 지시가 아니라서, 알아서 그럴듯한 기능을 상상해서 만들었을 가능성.

**다음에 반영할 것**: 에이전트에게 맡기는 스펙은 에이전트가 터미널에서 스스로 빌드→실행→관찰까지 검증 가능한 범위로 한정. 온디바이스/블루투스/실기기 필요한 기능은 사람이 직접 붙어서 확인하는 별도 체크리스트로 분리하고, 에이전트에게는 순수 로직/네트워킹/데이터 레이어처럼 시뮬레이터·유닛테스트로 검증되는 부분만 맡기기.
